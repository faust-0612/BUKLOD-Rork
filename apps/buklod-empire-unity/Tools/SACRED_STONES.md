# Sacred Stones — approved economy, isolated DEV
- Every canonical hero has a distinct community mission and Kingdom discovery location. All 13 cost exactly 100 claimed, spendable BP; no hero or Diamond surcharge. One corresponding stone per confirmed human hero pick, one additional matching stone for an optional opponent hero ban. At most one ban per team. No combat bonuses from payment or mastery. Training is free.
- Same inventory for BUKLOD, Kingdom and Empire. Gifts move stones atomically. Direct purchase uses platform-approved billing and verified receipts; no cash-out, QMP changes or real-money player-to-player sale. No PHP price set yet. Bundles are equal-value by stone type. No paid random loot.
- Kingdom free discovery sources: rare pick, quest, monster drop, treasure and village rewards. The trusted quest server verifies unique evidence, eligibility and anti-farming before granting. Distinct mission/location IDs live in Assets/Resources/StoneEconomy.json; all 13 should have comparable effort and opportunity. Drop rates and reward caps are server configuration to be balanced by telemetry; no client-side random minting. Battle rewards also require trusted match verification.
- SQL candidate is Tools/sacred-stones-server-candidate.sql, intentionally outside migration paths. It models a private shared wallet, immutable operation and ledger, atomic canonical BP debit, gift, verified receipt/reward, match reserve/start/complete/cancel/invalid and expiry refund. No public RPC or privileges granted. Never apply against live MAIN as-is.
- Required integration before release: verify current BP balance triggers, allowed debit activity types, reservations and shared lock order; account eligibility (exclude official/system account), auth ownership and rate limits; one trusted service adapter for all three surfaces; verified billing and refund/revocation policy; canonical quest evidence and drop balancing; authoritative multiplayer match roster/draft/start/invalid outcomes; expiry worker; signed client API; Unity inventory and draft UI, Kingdom actual quest hooks, PostgreSQL concurrency/RLS tests, Android runtime tests. The offline battle simulation stays training-only and cannot award tradable stones. No new Supabase project or production changes.
- Refund when reserved match cancels or verified server-invalid match; completed matches and normal disconnects are not refunded. Repeated requests must reuse their keys; final draft must have stable action order on retry. No indefinite reservation or client settlement.

## Arena-only extensions
- 13 fixed recipes (two adjacent stones in canonical roster -> center stone), 3 any non-target stones -> chosen base stone. No new gems or crafting items. No random failure. Exact matching recipe and quantity validation; atomic debit-before-credit. Direct and multi-gem trades must exchange equal counts; opt-in wishlist suggestions, explicit recipient acceptance, expiry, cancellation. Gift requests and sponsorship transfer one matching stone with consent. Emergency summon/ban use conversion before final draft; draft swap requires both players' confirmation and revalidation before reserve_match. No swapping after reservation; cancel/refund and create fresh match ID if needed. Team synergy is existing skill strategy only.
- Counter: proposed tuning 4s, 20% reduction to matching hero's relevant cast effect, range 12 simulation units, one reserved per player; no stacking, at most one activation per target per match. Vhen's turret duration is reduced (his actual kit has no native regeneration skill). Counter costs one matching stone only if activated; unused reservations refunded on normal completion; all refunded for cancelled or server-invalid match. Offline practice is free, no tradable wallet; TryPracticeCounter is the simulation API, no HUD wiring yet. Ranked counters disabled until equal non-paid competitive opportunity and balance are independently verified. Casual is explicitly selected by trusted match server, not inferred from client.
- Backend candidate adds private conversion, offer/accept/cancel, wishlist matching, gift requests and counter reservation/activation/refund. Sponsor using gift or accepted request, not a cash purchase. Server adapter must authenticate caller, validate membership, block abuse, enforce rate limits, verify consent and canonical mode, perform range/alive/tick checks, and deliver/replay a durable activation event without duplicate effects. UI/draft swap handshake, secure adapters, actual PostgreSQL concurrency tests and Unity tests remain release gates. All changes DEV only.

Draft swap now has explicit two-party consent, matching-wallet and ban preflight in ArenaStoneRules; same-team duplicate picks are rejected by the SQL candidate. Team synergy suggestions are available as a pure lineup query, not a combat modifier.

Offline training menu now includes a free practice counter button against the nearest eligible enemy hero, disabled when paused, finished, outside range or already used. This is a simulation demonstration; the eventual online UI must select the reserved stone and exact enemy, show a visible target warning, and consume only a verified activation. No online wallet is touched.

## Kingdom mastery quest integration (DEV)
Actual hook: existing KingdomMasteryCheck calls the authenticated self-scoped inventory sync after a credited or already-credited check. The server looks up the exact 39 canonical games, three per hero, and requires each to have both a credited attempt and matching +2 BP ledger evidence. One matching stone per hero/account after three verified checks; existing verified achievements qualify; no replay reward. A missed sync is recovered when opening the treasury. This is a bounded mastery milestone, not a claim of real-time monster, rare pickup, treasure or village events. Those still need trusted gameplay evidence. No changes to existing Shards, mastery BP or Character System.
The separately gated SQL facade is in Tools/sacred-stones-kingdom-candidate.sql. Both master enable and BP exchange flags default false. It is NOT a deployed migration; only after local tests, live-schema compatibility review and frozen RC may it be applied. Client inventory/combination/exchange/gift/request/trade UI is in the existing Kingdom rewards screen; user-scoped server snapshots only, explicit UUID recipient, same request retry. Direct purchase, authoritative Arena matchmaking, repeatable gameplay rewards and Unity authenticated transport remain separate release blockers. No live changes.

Recovery: the treasury persists at most one pending action per account before network submission, retries its exact UUID, and uses the authenticated request receipt/tombstone endpoint to resolve uncertain results without risking a duplicate spend. Server business actions and the receipt commit atomically. Rate limiting is a successful-transaction quota only; edge abuse controls still required.

`Tools/test_sacred_stones_kingdom.sql` is the guarded local fixture for disabled defaults, 3/3 evidence (including missing BP proof), account isolation, official exclusion, replay, cancelled requests and private grants. `tests/arena-sacred-stones-kingdom.test.mjs` checks the 39-to-13 mapping and the actual client wiring. Neither fixture authorizes release.

## Repeatable discovery (DEV)
A third private SQL candidate, Tools/sacred-stones-discovery-candidate.sql, adds persisted discovery outcomes, common daily caps (one awarded stone, 12 eligible rolls across repeatable sources), and private world-session/object hooks for rare pickups, monsters, treasure, village and quest rewards. All rates are equal across hero types. Starting tuning: 5%, 8%, 12%, 15%, 20% respectively; free only. A server-scored repeatable Kingdom supply-puzzle trial is wired in the existing Treasury, three attempts per Manila day, 20% after three correct answers. It is a new actual server-side trial, not proof of real-time monster combat. World adapters remain disabled until an authoritative simulation proves events; the private hooks must never be invoked directly by a player client. Existing mastery milestone stays separate. Both discovery flags default false. No changes to live database or production.

## Authoritative turn-based Kingdom expedition (DEV)
`Tools/sacred-stones-expedition-candidate.sql` adds a playable daily five-stage route using the same private world discovery hooks: rare pickup puzzle, turn-based monster combat (server-owned HP and telegraph), treasure lock, village supplies and final quest requiring all four objectives. The server, not the UI, selects source/object IDs and decides rewards. Per-account/day route uniqueness, session expiry, two-second turn delay, versioned action and request replay protection; no paid entry. It shares the existing repeatable discovery cap and requires both expedition and world-discovery gates, default false. Existing real-time Arena/Kingdom engines remain unconnected; this route is a separate turn-based activity, not a replacement or proof of their gameplay. No live migration applied.

Expedition hardening: supply puzzles always have a nonnegative answer, expired routes close their private sessions, turn countdown uses server-relative time, and wallet refresh is limited to route resume or a new granted stone. No new Unity 3D scene or multiplayer engine is claimed.
